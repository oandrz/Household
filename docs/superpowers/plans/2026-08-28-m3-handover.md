### Branch off `main`, and pull it first

The plan says M3 branches off `main` once M2 has merged. **PR #11 is still
open**, so either wait for it or say plainly in your PR that you branched off an
unmerged tree.

```bash
git checkout main && git pull --ff-only && git log --oneline -1
git checkout -b ui-consistency
```

The `git pull` is not ceremony. The last agent branched from a local `main` that
was one commit behind `origin/main`, caught it before writing code, and would
otherwise have re-litigated all of M1's diff inside M2's PR. `git fetch` alone
does not move `main`. Confirm the SHA after pulling.

`ui-polish` and `ui-defects` were both squash-merged or are pending as squashes,
so their commits are **not** ancestors of `main` even when the content is in it.

## 3 · Things that will bite you

The first four are inherited from the previous handover and are all still true.
The last three are new, and each cost the M2 agent time.

**`go` is not on `PATH`, and the Docker socket is not configured.** Export all
three before any `go` command or any `make` target that shells out to one. The
Go suite uses testcontainers and takes about four minutes.

```bash
export PATH="/Volumes/Oink_Machine/.local/opt/go-v1.24.2/bin:$PATH"
export DOCKER_HOST=unix:///Volumes/Oink_Machine/.colima/default/docker.sock
export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
```

M3 changes no Go, but `make test` runs the Go suite and `make lint` runs
`go vet`, so you still need them for the gate in Task 18.

**Never pipe a gate.** `make test | tail` reports `tail`'s exit code. This is
not hypothetical twice over: one agent reported a failed run as passing, and the
M2 agent's own run came back `TEST_EXIT=2` while the last visible line of the
log was `ok`. Capture the exit code and grep the log for `FAIL` separately:

```bash
make test > /tmp/test.log 2>&1; echo "TEST_EXIT=$?"
grep -nE "^(FAIL|--- FAIL)" /tmp/test.log
```

**The Go suite has an occasional testcontainers flake.** M2 hit
`TestMembershipRepoRoundTrip` failing with `connection string: port "5432/tcp"
not found` — testcontainers failing to read a port mapping, once, in a package
nothing had touched. The re-run was clean. Re-run before you go hunting; do
**not** assume a failure is a flake without re-running and confirming it.

**Two browsers are available and they are not equivalent.** The Claude-in-Chrome
browser sets `:hover` matching but does **not** repaint CSS hover styles — an
earlier agent nearly filed a false bug against `GoalCard` because of it. Use a
real CDP browser for anything involving hover, focus, or computed style. M3 is
almost entirely about surface, weight and colour, so this matters here more than
it did in M2.

**The chrome-devtools MCP browser may refuse to attach** with `The browser is
already running for .../chrome-profile. Use --isolated`. The M2 agent hit this
and used the **Playwright MCP** instead, which drives real Chromium over CDP —
real input, real focus, real computed styles. It works; reach for it directly
rather than trying to free the devtools profile.

**Mutation-check the code, not the comment.** The M2 agent ran a mutation with a
Python string-replace that matched a sentence in a **file header comment**
before it reached the line of code with the same text. The suite stayed green
and the check looked like it had proved the test was decoration. It had proved
nothing. After every mutation, `grep` the line you meant to change and confirm
it actually changed before you believe the result.

**Beware `git checkout -- <file>` on unstaged work.** The same agent used it to
undo a one-line mutation and reverted an entire unstaged fix along with it —
`checkout --` restores from the index, not from "before my last edit". Copy the
file to `/tmp` first, or stage the fix before mutating.

**The dev database is not what the previous handover describes.** M2's walk
needed states that did not exist on this box, so they were created through the
UI: an **achieved goal** ("Japan 2027", S$10 of S$10, target Apr 2027), an
**August budget** (Food capped at S$800), and a **S$2.00 "Kopi" expense** dated
2026-08-28. The seeded household from `make seed`
(`andreas@hearth.family` / `hearth-dev-password`) still has a populated ledger
and several members. **Check which household you are signed into before
concluding a screen is fine.**

For M3 specifically you will need:

- **Task 15** — a household with **every bill paid, and at least one bill**, to
  reach "All caught up". Neither household had bills as of M2. You will
  probably have to add a bill and mark it paid to see this panel at all.
- **Task 16** — any household with accounts; the breakdown card is on `/money`.
- **Task 17** — `/marriage/retros` with **no retro selected**. Trivial to reach.

**The repo means it about browser verification.** CLAUDE.md records that the
product owner asked for it explicitly on 2026-07-30. It is not a formality on
this milestone: all three M3 tasks are about how something *looks* against its
neighbours, which no test in this repo can assert. jsdom has no CSS cascade and
no layout — a test that checks a class string is present says nothing about
whether the surface reads as a card. M2's walk found two real defects nothing

## 4 · One thing M2 learned that M3 should apply

**When you change something shared, sweep its readers in the same change.** M2's
month-contract fix gave a previously-neutral default a meaning, and the endpoint's
*other* caller — `RecentTransactionsCard`, whose own comment explained that it
passed `{}` precisely because that was the same question as the ledger's default
— silently became "recent transactions this month". Five rows became one, and on
the first of any month it would have shown a household with years of history
nothing at all. No test on either side could catch it: `stubFetchRoutes` matches
exact URLs, so a stub is blind to the server's meaning of a request moving, and
the card returns `null` on a query error, so a wrong URL throws into a component
that renders nothing and a suite that stays green.

M3's analogue is smaller but the same shape: **`BreakdownCard` and `BillsPage`
are not the only readers of the classes you are about to change.** Before you
alter a shared surface string, grep for it. If you change a token in
`index.css`, grep every consumer. Three panels is the task; the class is every
panel that shares the pattern.

`docs/LEARNING.md` pattern 1 is now eighteen bullets long, and the count is the
number of bullets — recount it if you add one.

## 5 · Definition of done

From CLAUDE.md, and Task 18:

- `make lint && make test` green **on the tree you are integrating** — run it as
  the last thing before the PR, not forty-five minutes earlier. `docs/LEARNING.md`
  records a whole-branch review that passed a gate produced from a tree that
  predated the change it was certifying.
- **At least one new test mutation-checked.** M3 is mostly class strings, which
  are weak things to test; if a task genuinely has no assertion worth writing,
  say so in the PR rather than writing a test that cannot fail.
- **`docs/LEARNING.md` updated.** Task 18 names the entry: three panels each
  diverged from the surface, weight or empty-state shape their own siblings
  used. What would have caught it sooner is reviewing a new panel against **the
  page it joins**, not against the design file alone.
- **`docs/FEATURE_TRACKER.md`** — check it, but M3 changes no feature's state,
  so it most likely needs nothing. Say in the PR that you checked and why
  nothing moved; a tracker nobody checked and a tracker that needed no change
  look identical afterwards.
- **`docs/SYSTEM_DESIGN.md`** needs nothing: no route, table, port, service or
  request flow changes in M3.
- **Walk it in a browser** at desktop and 390px, per §3.
